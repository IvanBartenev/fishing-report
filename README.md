#  Fishing Report — Прогноз клева по атмосферному давлению

**Fishing Report** — это веб-приложение, которое помогает рыболовам выбрать идеальный день для ловли рыбы, анализируя атмосферное давление. 

Вместо того чтобы гадать, программа запрашивает прогноз погоды, рассчитывает стабильность давления по специальной формуле и выдает оценку каждого дня от 0 до 100. Идеальный день — это стабильное давление или его плавное снижение.

##  Возможности (MVP)
- **Поиск по городам:** Ввод названия города (с поддержкой синонимов, например, «Питер» → Санкт-Петербург).
- **Выбор периода:** Прогноз на 7 или 14 дней.
- **Умный скоринг:** Бизнес-логика штрафует за резкие скачки давления и аномальные отклонения от нормы, но поощряет плавное снижение.
- **Визуализация:** Интерактивный график с двумя осями (баллы и само давление в мм рт. ст.) и подсказками с объяснением оценки.
- **Кэширование:** Защита от лишних запросов к API (данные хранятся в памяти 1 час).

##  Архитектура проекта
Проект спроектирован с прицелом на дальнейшее расширение (добавление новых API, баз данных и т.д.):

- `app/providers/` — адаптеры к погодным API (реализация: Open-Meteo).
- `app/domain/` — чистая бизнес-логика (расчет баллов), не зависит от API и HTTP.
- `app/api/` (в `main.py`) — слой FastAPI, принимающий запросы.
- `app/templates/` — фронтенд (HTML + Chart.js).
- `app/cache/` — простой кэш в памяти для оптимизации запросов.
- `tests/` — юнит-тесты для бизнес-логики (Pytest).

##  Стек технологий
- **Backend:** Python, FastAPI, Uvicorn
- **Frontend:** HTML, Vanilla JS, Chart.js
- **Источник данных:** Open-Meteo API (геокодинг, прогноз, архив)
- **Тестирование:** Pytest

## Почасовой анализ (Этап 2)

Почасовой индекс условий — это интерпретируемая эвристическая оценка,
основанная на изменениях давления за скользящие интервалы 3, 6, 12 и 24 часа.
Это не вероятность поклёвки и не прямое измерение активности рыбы.

Оценка согласованности ансамблевого прогноза рассчитывается по 10-му, 50-му
и 90-му процентилям почасового индекса, отдельно рассчитанного для каждого
участника ансамбля. Отображаемый разброс показывает степень расхождения
между участниками модели; это не калиброванный вероятностный интервал.
Если для временной точки доступно менее пяти траекторий участников ансамбля,
оценка согласованности помечается как недоступная.

Существующий модуль дневного скоринга намеренно не изменялся.


## Почасовой API (Этап 3)

`GET /report/hourly?city=Воронеж&date=YYYY-MM-DD` возвращает почасовые
значения давления и эвристический индекс условий от 0 до 100 за один
календарный день. Endpoint принимает только текущую дату по московскому
времени и две следующие календарные даты.

Процентили ансамбля объединяются с детерминированным прогнозом по точным
локальным временным меткам. Если ансамблевый сервис недоступен, endpoint
всё равно возвращает почасовые значения детерминированного прогноза и
указывает, что оценка согласованности недоступна. Нижняя и верхняя границы
в этом случае остаются равными `null`, а не подставляются искусственно.

Существующий endpoint `/report` и дневной модуль `scoring.py` не изменялись.


## Почасовой интерфейс (Этап 4)

Интерфейс отображает карточки первых трёх дней прогноза. При раскрытии
карточки почасовые данные загружаются по запросу через `/report/hourly`;
одновременно может быть открыта только одна карточка.

На почасовом графике используются отдельные оси для атмосферного давления
и индекса условий. Диапазон 10–90-го процентилей ансамбля отображается
только в том случае, если API вернул соответствующие данные.

Предусмотрены состояния загрузки, ошибки и повторной попытки. Отсутствующие
значения дневного давления отображаются как пропуски на графике, а не
заменяются искусственно заданным нормальным значением.


## Проверка Open-Meteo на реальных данных (Этап 5)

Запустите `python scripts/smoke_open_meteo.py [city]` из корневой папки
репозитория в среде с доступом к интернету. Скрипт запрашивает
детерминированный и ансамблевый прогнозы на 72 часа, проверяет соответствие
часовых поясов, точное совпадение временных меток и количество доступных
участников ансамбля.

Провайдер Ensemble отправляет только параметры, документированные в API.
Почасовое временное разрешение соответствует штатной почасовой выдаче API
(в том числе интерполированной, если это предусмотрено сервисом).
Ранее использовавшийся недокументированный параметр
`temporal_resolution` удалён.

Проверить реальные сетевые запросы в среде сборки не удалось, поэтому
smoke-тест необходимо запускать на локальном компьютере пользователя
или на развёрнутом сервере.
